# Commit

현재 작업 트리의 변경사항을 정확히 파악하고, 사용자가 의도한 변경만 하나의 일관된 커밋으로 남긴다.

## 안전 원칙

- 커밋과 push를 구분한다. 이 스킬은 기본적으로 로컬 커밋까지만 수행한다.
- 사용자가 명시적으로 요청하지 않은 변경사항을 수정, 삭제, reset, checkout, stash, amend하지 않는다.
- 기존 작업 중인 변경사항이 있으면 먼저 범위를 확인한다. 이번 요청과 무관한 변경사항은 커밋에 포함하지 않는다.
- 커밋 메시지, diff, 검증 결과에 포함될 수 있는 비밀값(API 키, 토큰, 인증서, `.env` 값)을 확인한다. 노출 가능성이 있으면 커밋을 중단하고 사용자에게 알린다.
- 커밋 전에는 실제 staged diff를 다시 확인한다. `git add .` 또는 저장소 전체를 무차별적으로 스테이징하는 방식은 피한다.

## 워크플로

### 1. 저장소 지침과 상태 확인

저장소 루트에서 가까운 순서의 `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, 커밋 관련 문서를 찾아 읽고 적용한다. 하위 디렉터리에 더 가까운 지침이 있으면 해당 경로의 파일에 우선 적용한다.

다음 정보를 확인한다.

- 현재 브랜치와 저장소 상태: `git status --short --branch`
- 추적/미추적 변경사항과 파일 목록
- 최근 커밋 메시지 형식: `git log -5 --oneline` (커밋이 있을 때)
- 프로젝트의 적절한 lint, typecheck, test, build 명령

저장소에 변경사항이 없으면 커밋을 만들지 않고 사용자에게 알린다.

### 2. 변경 범위와 의도 검토

`git diff`와 필요하면 `git diff --stat`, `git diff -- <path>`로 변경 내용을 읽는다. 미추적 파일은 내용과 크기를 확인한다.

- 요청과 직접 관련된 파일만 후보로 삼는다.
- unrelated 변경, 생성된 산출물, 캐시, 의존성 디렉터리, 로컬 설정은 제외한다.
- 한 커밋에 함께 있어야 하는 변경인지 판단한다. 서로 독립적인 변경이 섞여 있으면 가능한 경우 각각 별도 커밋으로 나눈다.
- 변경 의도가 불명확하거나 사용자가 어떤 변경을 커밋할지 지정하지 않았다면, 추측으로 커밋하지 말고 후보 파일과 이유를 보여준 뒤 확인을 요청한다.

### 3. 필요한 검증 실행

변경의 위험도에 맞는 가장 가까운 검증을 실행한다. 저장소 지침이 있으면 그것을 우선한다.

- 문서나 설정만 바뀐 경우에도 diff와 형식 오류를 확인한다.
- 코드가 바뀐 경우 관련 테스트와 lint/typecheck를 우선 실행한다.
- 검증 명령이 없거나 실행할 수 없으면 그 사실과 이유를 커밋 결과에 명확히 남긴다.
- 실패한 검증을 성공한 것처럼 표현하지 않는다. 실패가 변경과 관련되거나 심각하면 커밋을 중단하고 사용자에게 보고한다.

### 4. 선택적으로 스테이징

검토한 파일 경로를 명시해 `git add -- <path>...`로 스테이징한다. 이미 staged인 변경도 `git diff --cached`로 확인하고, 사용자의 변경을 덮어쓰지 않도록 한다.

다음 명령으로 최종 내용을 검토한다.

```text
git diff --cached --stat
git diff --cached
git status --short
```

staged diff가 의도한 범위와 다르면 커밋하지 않는다. staged 변경을 되돌려야 하는 경우에도 파일 내용을 삭제하지 않는 `git restore --staged -- <path>`처럼 비파괴적인 방법을 우선하고, 사용자의 기존 staging 상태를 보존한다.

### 5. 커밋 메시지 작성과 커밋

프로젝트에 정해진 형식이 있으면 따른다. 별도 형식이 없으면 짧고 명령형인 제목을 사용한다.

- 제목은 변경의 결과를 설명하며, 가능하면 72자 이내로 작성한다.
- `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:` 같은 Conventional Commits 형식은 기존 저장소가 사용하거나 사용자가 요청한 경우에만 따른다.
- 한 커밋에는 하나의 논리적 목적만 담는다.
- 사용자 요청 없이 `--amend`, 서명 옵션, hook 우회(`--no-verify`)를 사용하지 않는다.

커밋 직전 사용자 확인이 필요한 환경이나 사용자가 확인을 요구한 경우에는 제목과 staged 파일 목록을 제시하고 멈춘다. 그 외에는 요청된 범위 안에서 `git commit -m "..."`을 실행한다.

### 6. 결과 보고

커밋 후 다음을 확인해 결과를 보고한다.

- 커밋 해시와 메시지
- 커밋에 포함된 파일 요약
- 실행한 검증과 결과
- 아직 남은 작업 트리 변경사항

push는 자동으로 수행하지 않는다. 사용자가 push도 요청한 경우에만 원격, 브랜치, 인증 상태를 확인한 뒤 별도 작업으로 진행한다.

## 중단 조건

다음 상황에서는 커밋하지 않고 현재 상태와 필요한 결정을 사용자에게 묻는다.

- 커밋 대상 파일이나 변경 의도가 불명확함
- staged diff에 요청과 무관한 변경이 포함됨
- 비밀정보가 포함되었거나 포함되었을 가능성이 있음
- 핵심 테스트, lint, typecheck가 실패함
- 병합 충돌, rebase 진행 중, detached HEAD 등 저장소 상태가 일반 커밋에 적합하지 않음
- 커밋을 위해 기존 작업을 삭제하거나 되돌려야 함
